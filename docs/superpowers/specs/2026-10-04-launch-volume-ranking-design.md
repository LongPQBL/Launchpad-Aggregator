# Launch list: two tabs with global 24-hour USD volume ranking

Date: 2026-10-04

## Intent and decisions

The owner wants to remove `Trending`. `All` should rank launches across the complete filtered data set by official 24-hour trading volume converted to USD. `Recently launched` should show newest launches first. Both tabs retain the existing search, lifecycle, launchpad, chain, and next-page behavior. The owner chose USD as the common unit because Pons launches use WETH, native ETH, USDG, and stock-token quote assets. The owner confirmed that “official venue” means the already verified venue history of each Pons launch, including executed protocol activity. The owner later clarified that the product will also have a Uniswap-like `Pools` section containing other pools; its swaps need the same USD pricing infrastructure. Pool discovery, ingestion, and their product metrics require a separate design.

Uniswap's Launches UI uses a separate server-side trending ranking, so the previous local `change1h` sort does not meet this product goal. This project will have two tabs only. This change affects the API read path and frontend; new indexing work must use Envio, and this feature does not extend the legacy RPC indexer.

Three approaches were considered. Sorting the fetched page is cheap but gives a false global order. Sorting raw quote amounts across launch assets misranks WETH, USDG, and stock-token pairs. A persistent Envio-maintained volume table is scalable but adds write-path and reorg logic immediately. The chosen path is a measured read-side aggregate of per-trade USD values at the time of execution, with a persistent historical quote-price source. An Envio-maintained summary is required if that read path misses the performance gate below.

This valuation follows the published behavior of [Uniswap's V3 subgraph](https://github.com/Uniswap/v3-subgraph/blob/main/src/v3/mappings/swap.ts), which assigns USD value while handling each swap and then adds it to volume, and [Dune's `dex.trades`](https://docs.dune.com/data-catalog/curated/dex-trades/evm/dex-trades), whose `amount_usd` is the trade's USD value at execution time. Repricing the entire 24-hour quote total with today's price would make past trades change value when the quote asset moves, so that shortcut is rejected here. The same historical valuation also replaces the current-price USD estimate in individual transaction rows.

Uniswap's V3 subgraph adds a valued swap to both its pool volume and each involved token's volume. Its [Explore Pools](https://app.uniswap.org/explore/pools) view reports volume per pool, while [Explore Tokens](https://app.uniswap.org/explore/tokens) describes token volume across Uniswap trading. The public sources inspected do not establish the exact pool set behind Uniswap's separate Launches ranking. In this project, keep `officialVolume24hUsd` for the launch's verified official venues as previously chosen. The future `Pools` section has per-pool USD volume from its own verified swaps, using the same price infrastructure. If the product later displays volume across all indexed pools for a token, name and label that metric separately; do not silently add non-official pools to `officialVolume24hUsd` or count a swap twice.

## Existing behavior and constraints

- `fe/src/features/launches/launch-list.tsx` sorts only the current page for Trending. All and Recently launched both receive the backend's launch-recency order.
- `be/src/api/store.ts` limits the launches query before computing per-row `officialVolume24h`. Sorting those returned rows cannot produce a global rank.
- `officialVolume24h` is in each launch's quote asset, so its decimal amount is not a cross-asset ranking key. The existing Chainlink pricing reader verifies quote-asset feeds by address and rejects stale or invalid prices, but it only reads the latest price. The existing trade API's `usdValueApprox` also uses the latest price; this ranking must not inherit that shortcut.
- `listTrades()` currently reads one latest Chainlink price for the whole page and multiplies every trade's quote amount by it. The transaction table tooltip explicitly calls this an approximation at the current price. A historical trade's displayed USD value can therefore change with today's quote price.
- The real `trades` table currently has about 3.2 million rows and is about 3.5 GB. Its timestamp index begins with `(chain_id, token_address)`, which does not directly support a global trailing-24-hour scan. Measure the actual plan and latency before accepting a request-time aggregate.
- A launch's `coverageStatus` is determined from its required factory, lifecycle, and official trading sources against the Envio-aware safe head. A missing window must never be presented as genuine zero volume.

## API and ranking behavior

`GET /v1/launches` gains `sort=volume24hUsd|recent`. Keep the API's omitted-sort behavior as `recent` for existing callers; the frontend explicitly requests `volume24hUsd` for All and `recent` for Recently launched. An unknown sort returns 400. Search, status, platform, and chain filters apply before ranking; every page uses the same global order.

For `volume24hUsd`, select indexed trades in `[asOf - 86400, asOf]` for each launch's official venues (`venues.official = true`). Take each trade's raw quote amount once, using the launch's quote decimals. Include executed protocol buybacks and internal swaps already stored as trades; do not count fee transfers or non-trade events. Reuse the existing per-launch coverage rule when deciding whether the number can be ranked.

For each trade, use its recorded quote-asset address to select the feed, then convert its quote amount with the latest verified quote/USD price round known before that trade's onchain position. Use the round's publication block and log position when available; a round in the same block must precede the trade log. If publication order cannot be proved, use the latest round from an earlier block. Its `updatedAt` must also be at or before the trade timestamp. Reject a nonpositive answer, an invalid timestamp, an untrusted feed/address mapping, or a round older than the feed's permitted freshness interval at that trade time. Persist round IDs, answers, decimals, timestamps, and available publication positions for the supported feeds. Chainlink documents historical rounds through [`getRoundData`](https://docs.chain.link/data-feeds/historical-data); inventory actual feed coverage and available history for WETH, ETH, USDG, and stock-token quotes before implementation. Fetch and refresh rounds through an Envio-associated pricing workflow, with retries and observability; no per-trade RPC reads and no legacy-indexer write path. A verified direct USD quote may use an explicitly documented 1:1 rule only if its asset and the rule are trusted; do not assume every stable-looking token is one dollar.

Keep the quote/feed mapping in one place. Group pricing code and the reviewed seed mappings under `be/src/market/quotePricing/`, replacing the split hardcoded `FEEDS` map in `usdPricing.ts` and in-memory `quoteFeedRegistry.ts` as independent sources of truth. Persist discovered mappings in a `quote_usd_feeds` table keyed by `(chain_id, quote_asset_address)`, with the verified feed address, discovery source, verification status, and last-check time. This table is the runtime inventory; the code directory owns validation and discovery rules, not a manually edited list of every token. Match by chain and exact asset address, never symbol alone. Reuse Robinhood's canonical asset-address directory and Chainlink's feed directory as candidate sources, then verify the proposed feed and its quote/USD denomination before marking it usable.

When Envio sync records a Pons launch's declared quote asset or an official venue trade with a previously unseen quote-asset address, enqueue one deduplicated feed-resolution job for that address. The future Envio-based `Pools` ingestion uses this same registry and price-round store: after verifying a pool's identity and swap data, it submits the address of the asset leg used for USD valuation. This includes pools outside a launch's official venue history. A pool has two assets and no inherent quote side; choose a verified priced leg from the actual swap amounts and count its USD value once, rather than assuming token0/token1 or summing both sides. Unknown symbols or arbitrary unverified pool claims cannot supply a trusted feed mapping. A new asset does not block trade indexing. Once a USD feed is verified, backfill its price rounds for the rolling 24-hour window plus the last valid predecessor round, then make the affected pool or launch metric priceable. If no trustworthy feed exists, keep USD values unknown and retry feed discovery when the source directories refresh; never assume an unknown asset equals USD or attach a feed based on matching symbols alone.

Backfill the verified known quotes before enabling USD sort, then proactively maintain the rounds needed for the rolling 24-hour volume window for quote assets that actually occur in official trades. Do not scan all historical rounds for every quote asset at startup. Keep verified rounds already fetched in the DB. When a requested transaction page contains older trades whose price history is absent, enqueue one bounded, deduplicated backfill per feed and missing time range; do not fetch rounds synchronously per trade or hold the API request open on RPC. Backfill must have a durable retry state, and a transient RPC failure must not become a permanent unavailable value. A quiet launch whose first transaction page is already older than 24 hours follows this same demand path.

Sum the per-trade USD values to obtain `officialVolume24hUsd: string | null`; retain `officialVolume24h` in quote units. Document in OpenAPI that the USD amount is approximate because oracle rounds are discrete observations, and expose `officialVolume24hUsdApprox: boolean` for positive priced values. Show `~$` for those values. A known zero-trade window with complete coverage has USD volume `0` even without a price. If any positive trade in a launch's window lacks a verified historical price, mark the launch's entire USD volume `null`, rather than publishing an understated partial total. An incomplete trade-coverage window is also `null`. Never turn either case into zero.

Use this same per-trade valuation in `GET /v1/launches/{chainId}/{tokenAddress}/trades`: each row's `usdValue` is its own quote amount times its historical quote/USD price, regardless of whether the row is inside the latest 24-hour window. Remove the current-price fallback. If its historical price is missing, keep the trade row and return `usdValue: null` and `usdValueApprox: false`. Add `usdValueStatus: priced|pending|unavailable` so the client distinguishes a requested backfill from a feed that cannot price the trade. A priced row remains approximate because an oracle round is a discrete observation, so `usdValueApprox: true`; update the OpenAPI description and transaction-table tooltip to say this is the historical quote price known at trade time. Reuse one valuation routine for individual trades and the volume aggregate to prevent disagreement.

Sort by known USD volume descending, then by the existing launch position descending, then `(chain_id, token_address)` for a total order. Real zero follows positive values; `null` follows known zero. Within the zero and null tails, use launch recency. `recent` keeps newest-first launch position order. A launch can move when new indexed trades, coverage, or a missing historical price round arrives; the UI should not claim that the ranking is immutable.

## Cursor and consistency

The volume cursor is distinct from the existing three-field recency/trade cursor. It records a version, sort mode, 24-hour window end (`asOf`), the last row's rank category/value, and its launch-position tie breakers. It must be signed by the API so a caller cannot forge a historical ranking date. Validate sort, numeric values, signature, size, and a bounded cursor age before use. Subsequent pages use the same window, so clock movement alone does not reorder the sequence. A cursor for one sort cannot be used with another sort. Existing `recent` and trade cursors retain their current format. Newly indexed historical trades, late historical price rounds, or a reorg can still change rankings during an open pagination sequence; this limitation is explicit and tested where practical.

## Query and performance approach

Start with a read-side query over the authoritative `trades` and `venues` tables, `quote_usd_feeds`, and a historical `quote_usd_price_rounds` table keyed by chain, feed, and round ID, with an index that finds the newest round provably before a trade's chain position and within its freshness interval. Benchmark it against a representative local copy of the current database. Add a timestamp-leading trades index for the 24-hour scan if the measured plan needs it. Because the live trades table is multi-GB, create that index concurrently in the deployment procedure; do not put a blocking index build in the normal transactional migration path. Avoid per-trade or per-launch RPC calls and per-launch trades queries across the 160K+ launch set. Missing feed coverage or missing required historical rounds gives the affected launch a null ranking; a temporary round-sync failure is observable and retried by the pricing workflow. Persist verified rounds, never a permanent null score from a transient RPC failure.

The implementation is accepted only if the first and subsequent filtered pages complete comfortably within the frontend's eight-second API timeout on representative data, and repeated requests do not overload the DB. If a request-time aggregate cannot satisfy that gate, use an Envio-fed rolling volume summary and reorg-aware recomputation before shipping this ranking. No writes are added to the legacy indexer.

## Frontend behavior

- Show exactly `All` and `Recently launched`; remove the Trending client-side sorter and its tests.
- The default All route requests USD-volume sort. Recently launched requests recency sort. A stale `?tab=trending` link resolves to All and does not keep a hidden Trending state.
- Preserve tab, filters, and sort on next-page links and search submissions; changing tab or filter starts at page one.
- The 24H volume cell shows approximate USD when available and keeps the quote amount accessible (for example, in a title or secondary text). When USD volume is null, show the existing honest unavailable state rather than a fabricated rank or zero. Explain that the USD value uses historical quote-price observations near each trade, and that missing historical prices leave the USD rank unavailable.
- Transaction rows with `usdValueStatus=pending` keep their onchain amounts visible and show that historical USD is loading; refetch the current page with bounded backoff until the requested backfill completes. `unavailable` shows the honest no-data state. Browsing older transaction pages can trigger more backfill without blocking pagination.

## Verification

Write failing tests before implementation for: cross-quote USD order; an Envio-observed new quote triggering one address-keyed feed lookup and 24-hour-plus-predecessor backfill; an unsupported quote remaining unpriced without blocking trades; a newly published verified feed making that quote priceable after retry; a spoofed symbol or unverified pool never selecting a feed; two trades with different historical quote prices in one window; individual transaction USD values matching their contribution to volume and remaining stable when the latest price changes; a round published later in the same block never pricing an earlier trade; known zero versus null; incomplete coverage; official-venue-only volume; positive volume with a missing, invalid, or stale historical round; partially priced windows becoming null; a quiet launch's first old transaction page triggering demand backfill; deduplicated and retryable older-range backfill; pending-to-priced/unavailable UI state without blocking pagination; stable tie order and cursor traversal; cursor tampering/expiry/sort mismatch; all filters; preservation of the `recent` order and trade cursor; frontend tab and request wiring. Verify the generated OpenAPI/client types and run backend unit and integration suites, frontend tests, lint, typecheck, and build. Measure and record the query plan/latency on representative data. No live migration or deployment is part of writing the code.

## Out of scope

No Trending score, implementation of the future `Pools` discovery/indexing/UI, exact external market ticks at swap time, wallet/trading controls, indexer rewrite, or live deployment. The pricing registry and historical round store must be reusable by that future `Pools` subsystem. The other minor issues from the owner's list remain separate tasks.
