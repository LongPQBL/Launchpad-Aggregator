# V4 Pool Swap Design

**Approved scope:** real on-chain Swap execution for a connected browser wallet, against a Uniswap V4 pool — either a V2 launch's graduated official venue (launch detail page) or any V4 pool on the Pools-tab page (which, by construction, only ever lists pools containing at least one Pons-launched token — see CLAUDE.md's 2026-10-06 "Pools" scope correction). `docs/superpowers/specs/2026-10-06-v3-pool-swap-design.md` explicitly deferred V4 pool swap as "a separate, later follow-up" — this is that follow-up.

No platform fee, no cross-pool routing, no simulated/paper trading — same ground rules as curve trading and V3 pool swap. Unlike V3, this spec *does* use Permit2 signing (see "Approval architecture" below) — the earlier "no 1-click/permit2 session approvals" ground rule is narrowed for this spec specifically: it still excludes EIP-5792 wallet-call bundling (see "Explicitly out of scope"), but Permit2 itself is not optional infrastructure for V4 (Universal Router has no other way to pull ERC20 funds), so it is in scope.

## Why V4 needs its own spec, not just a copy of V3

V4's `PoolManager` is a shared singleton using flash-accounting: there is no way to call `PoolManager.swap()` directly from an EOA wallet. The call must originate from a contract that implements `IUnlockCallback` and settles payment inside that callback. On official Uniswap-supported chains, Uniswap Labs deploys and audits a canonical `UniversalRouter` contract for exactly this purpose; third-party aggregators and bots deploy their own equivalents. Robinhood Chain is not in Uniswap Labs' list of officially supported chains, so there was no *a priori* reason to assume an official Universal Router exists here — this spec's research task was first to find out whether one does.

## Protocol research (verified, not guessed)

- **Permit2 exists on this chain** at its canonical CREATE2 cross-chain address `0x000000000022D473030F116dDEE9F6B43aC78BA3` — confirmed via `eth_getCode` against the public RPC (`https://rpc.mainnet.chain.robinhood.com`), real bytecode (18,306 hex chars), not empty.
- **Pons's own V2 docs (`docs.ponsfamily.com/v2`) confirm the hook does not gate trading.** Quoted directly: *"A graduated launch trades as an ordinary Uniswap v4 pool holding the launch token and its quote asset. There is nothing pons-specific about swapping it, so any v4-aware router or aggregator can trade it without integrating against pons at all."* and *"The hook accrues fees but does not gate trading or restrict swappers."* Pons's docs list no Universal Router or other V4-specific router address — V4 trading is explicitly left to generic infrastructure.
- **A real Universal Router deployment was found**, but not by looking at top-level transaction recipients. Of 15 sampled real V4 `user_trade` transactions (joined from this app's own `trades`/`venues` tables, `kind = 'v4_pool'`), most route through the ERC-4337 `EntryPoint.handleOps` (Robinhood's own smart-account/AA infrastructure — confirmed via the `0x765e827f` selector decoding to `handleOps(...)` on openchain.xyz) or through a contract already flagged and rejected by the V3 spec (`0x4d819a2a` = a non-standard `swap(...)` signature, aggregator/bot-shaped). None of this is visible or useful at the top-level `tx.to`.
  - The useful signal is the `Swap` event's own indexed `sender` field — `event Swap(bytes32 indexed id, address indexed sender, int128 amount0, int128 amount1, uint160 sqrtPriceX96, uint128 liquidity, int24 tick, uint24 fee)`, emitted by `PoolManager` (`0x8366a39cc670b4001a1121b8f6a443a643e40951`) — this is unconditionally the real, direct caller of `PoolManager.swap()`, regardless of how many wrapper/AA layers sit above it in the same transaction. Decoding this field (not `tx.to`, not `tx.from`) across the same 15 samples surfaced `0x8876789976decbfcbbbe364623c63652db8c0904` as the `sender` in 3 of them.
  - That address's bytecode contains **both** documented Universal Router selectors: `execute(bytes,bytes[],uint256)` (`0x3593564c`) and `execute(bytes,bytes[])` (`0x24856bc3`). A live `eth_call` to `execute(0x, [], <future deadline>)` (empty commands/inputs) returned `0x` success — the documented no-op behavior of a real Universal Router, not a revert.
  - Its bytecode length (49,094 hex chars) did not byte-match any single canonical Universal Router deployment checked (Ethereum mainnet legacy at 39,000, Base at 39,000, a cited "2.1.1" mainnet address that turned out to have no code at all) — likely a different build/version/compiler than those specific deployments, or possibly a customized build. This is treated as **a real, functioning Universal Router-shaped contract**, confirmed functionally (selector dispatch + no-op success), not confirmed as byte-identical to one specific known Labs release. The exact command/action byte encoding this spec assumes (below) is Universal Router's long-stable, documented public interface, not something unique to any one release — but this is still flagged as **not independently decoded against a real non-trivial swap on this exact deployment**, same evidence gap the V3 spec had for native-ETH behavior.
- **Universal Router address for implementation:** `0x8876789976decbfcbbbe364623c63652db8c0904`.

## Approval architecture: Permit2 AllowanceTransfer via a signed `PermitSingle` ("Option B")

Two Permit2 approval mechanisms exist — `AllowanceTransfer` (a persistent, amount+expiration-bound allowance stored in Permit2, settable either by a plain on-chain `Permit2.approve()` transaction or by a signed `permit()` call) and `SignatureTransfer` (a single-use, non-persistent signed authorization for exactly one transfer). An earlier pass through this research briefly assumed Universal Router's V4 path used `SignatureTransfer` — reading `UniversalRouter`'s actual source directly (not just Uniswap's general Permit2 blog material) corrected this: `Dispatcher.sol`'s `PERMIT2_PERMIT` command (`0x0a`) decodes its input as `IAllowanceTransfer.PermitSingle` and calls `Permit2.permit(owner, permitSingle, signature)` — `AllowanceTransfer`, not `SignatureTransfer`. `V4Router`'s own settlement path (`DeltaResolver._settle` → `Permit2Payments.payOrPermit2Transfer` → `Permit2.transferFrom`, imported from `IAllowanceTransfer`) confirms the same: V4's token-pull step is an `AllowanceTransfer.transferFrom`, which requires a pre-existing (possibly just-signed-in-the-same-transaction) `AllowanceTransfer` allowance, not a `SignatureTransfer` permit.

- **A — plain two-step on-chain approval:** `ERC20.approve(Permit2, amount)`, then `Permit2.approve(token, UniversalRouter, amount, expiration)` (a direct transaction, not a signature), then the swap. No new signing code. 3 wallet transactions for a first-time token; later swaps reuse the standing allowance if it still covers the new amount and hasn't expired.
- **B — same persistent-allowance model as A, but the second step is a signature instead of a transaction (chosen):** `ERC20.approve(Permit2, maxUint256)` once per token (see "Why max approval here is still consistent with the existing policy" below), then, **only when the existing Permit2 allowance for `(token, UniversalRouter)` doesn't already cover the swap amount or has expired**, sign a fresh `IAllowanceTransfer.PermitSingle` EIP-712 message and bundle it as a `PERMIT2_PERMIT` command alongside `V4_SWAP` in the same `execute(...)` transaction. When the existing allowance already covers the swap, skip signing entirely and submit `V4_SWAP` alone. This is what Universal Router's real code does — not a theoretical option — confirmed by reading `Dispatcher.sol` and `V4SwapRouter.sol`/`Permit2Payments.sol` directly.

**Nonce:** `AllowanceTransfer`'s `PermitSingle.details.nonce` is read from `Permit2.allowance(owner, token, spender)`'s third return value (it increments with each successful `permit()` call for that `(owner, token, spender)` triple) — a live on-chain read immediately before constructing and signing each `PermitSingle`, not a client-generated random value (that generation method is specific to the unrelated `SignatureTransfer` interface, not used by this flow).

**Why max approval here is still consistent with the existing exact-amount policy, not an exception to it in spirit:** the policy's purpose is to avoid leaving a standing allowance that lets something move the user's funds without further authorization. A large `ERC20→Permit2` allowance does not have that property on its own: Permit2 still refuses to move a token for a given spender (Universal Router) until a separate, amount-and-expiration-scoped `AllowanceTransfer` allowance for that specific spender exists — set either by an explicit transaction or a signature the user approves each time it's needed. The `ERC20→Permit2` approval only grants Permit2 itself the general *capability* to move funds when properly authorized later; it is the per-spender `AllowanceTransfer` allowance (transaction- or signature-gated, amount- and time-bound) that is the actual authorization, and that step is never skipped. If this project later also moves V3 to Universal Router + Permit2 (noted below as a deferred follow-up, not in this spec's scope), the same reasoning would apply there too.

**Wallet-interaction count, stated precisely:** first-ever swap of a token is 3 wallet interactions (1 `ERC20→Permit2` approval transaction, 1 `PermitSingle` signature, 1 swap transaction). A later swap of the same token is 1 interaction (just the swap transaction) if the previously-granted `AllowanceTransfer` allowance still covers the amount and hasn't expired, or 2 interactions (a fresh signature + the swap transaction) if it needs renewing — never a second on-chain approval transaction, since renewing only ever needs a signature once the one-time `ERC20→Permit2` step is done.

## Quoting: a real, already-deployed MixedRouteQuoterV2 (no new contract needed)

`UniversalRouter.execute()` has no return value (`external payable`, confirmed from `IUniversalRouter.sol` directly) — unlike V3's `exactInputSingle`, simulating the real submission call cannot produce a quote the way `use-swap-quote.ts` does for V3. Uniswap's documented solution for this is a dedicated on-chain `Quoter`-family contract, called read-only via `eth_call` (it works by deliberately reverting with the quote ABI-encoded in the revert data). Uniswap's own hosted Trading API — what the official web app actually uses for quotes on chains it supports — does not cover Robinhood Chain, so an on-chain quoter (the SDK-documented fallback for exactly this situation) is the only real option here, same as it would be for any other unsupported-chain integration.

This repo has no Solidity/Foundry tooling, and deploying a fresh contract would have meant adding a new toolchain, a funded deployer wallet, and a new piece of owned on-chain infrastructure. Before taking that on, this was independently confirmed unnecessary: **`MixedRouteQuoterV2` is already deployed on Robinhood Chain at `0x7edd862aa08dD5Be664C21188E1A2A0E64e3A283`**, found by tracing the real deployer of the already-confirmed Universal Router back to its creation transaction (`0x422569c9...`, sender `0x9701fb0ade1e269c8f64ec0c7b3cfadb31a13a52`) and discovering that same address sequentially deployed the chain's entire recognizable official-style Uniswap stack in one burst around block 18,127–18,127 (WETH, four Permit2 calls, the real V3 factory `0x1f7d7550b1b028f7571e69a784071f0205fd2efa`, the Position Manager, `SwapRouter02`, then the Universal Router itself) — the same pattern of account that would also carry quoting infrastructure.

Independently verified (not taken on trust) with two live `eth_call`s against the project's own real fixture pool (`be/tests/fixtures/pons-v2-graduated.json`: token `0xc9e9ab90654f82893d7fd18b62f694992e8cef29` as `currency0`, quote asset `0xd0601ce157db5bdc3162bbac2a2c8af5320d9eec` as `currency1`, `fee: 0`, `tickSpacing: 200`, `hooks: 0xe5e702641ea86f4ae6cc3cdaed2b886f976be044`):

- `zeroForOne: true` (sell 1 token, 18 decimals) → `amountOut = 12,820,012,439` (quote wei), `gasEstimate = 105,006`.
- `zeroForOne: false` (buy with 1 quote unit) → `amountOut = 69,794,302,411,569,500,124,691,592` (≈69.79M tokens), `gasEstimate = 113,414`.

Signature used: `quoteExactInputSingleV4(QuoteExactSingleParams params) returns (uint256 amountOut, uint256 gasEstimate)`, where `QuoteExactSingleParams { PoolKey poolKey; bool zeroForOne; uint256 exactAmount; bytes hookData; }` and `PoolKey { address currency0; address currency1; uint24 fee; int24 tickSpacing; address hooks; }` — note the single-struct parameter shape (not four separate top-level parameters) and `exactAmount` as `uint256` here (this contract's own signature, not to be confused with `V4Router`'s unrelated `ExactInputSingleParams.amountIn: uint128`). The function is `nonpayable`, not `view` (same revert-based quoting mechanism as the standard `V4Quoter`), so it must be called via `eth_call`/`useSimulateContract`, never `view`-style state-change-free assumptions.

**`V4_QUOTER_ADDRESS = '0x7edd862aa08dD5Be664C21188E1A2A0E64e3A283'`** for implementation.

## Explicitly out of scope

- **EIP-5792 "1-click swap" bundling.** Uniswap's own "1-click swaps" feature (visible in the Trade options panel) is a wallet-capability feature (`wallet_sendCalls`/EIP-5792), not a property of the Permit2 flow itself — it requires the *connected wallet account* to support batched calls (smart-account mode; a plain MetaMask EOA does not, even though MetaMask the wallet app lists some 5792 support). The dApp side would need new code (`wallet_sendCalls` instead of separate `signTypedData`/`sendTransaction` calls) regardless of wallet capability. Deferred as a distinct future feature — Option B's signature flow is a clean foundation for it later (the signing step it already does is the same building block 5792 bundling would reuse), so choosing B now does not foreclose this.
- **Migrating the already-shipped V3 SwapPanel to Universal Router + Permit2.** Confirmed this is what Uniswap's own real interface actually does for V3 too (Universal Router replaced `SwapRouter02` as Uniswap's preferred entrypoint for all of V2/V3/V4). The existing V3 implementation (`fe/src/trading/swap-panel.tsx`, direct `SwapRouter02` calls) is not wrong — it is independently verified on this exact chain via a decoded real transaction and corroborated by `docs.ponsfamily.com` naming that exact address as "Swap Router" — just architecturally older-style than Uniswap's current app. Left as a noted, separate future follow-up; not touched by this spec. This means the app will have two different approve/sign architectures side by side (V3: plain approve; V4: Permit2 max-approve + per-swap signature) — an accepted, deliberate outcome, not an oversight.
- Multi-hop / cross-pool routing (same as V3 — single pool only).
- Any new backend/indexing work — `pool.fee`/`pool.hooks`/`currency0Decimals`/`currency1Decimals` are already available on `PoolSummary` (from the pool-decimals work shipped earlier this session) and on the official venue record for the launch-detail case; nothing new is needed there.

## Components and reuse

- **Reused as-is, no changes:** `ApproveOrActionButton`, `useRefetchQuoteAfterApproval`, `use-trade-settings.ts` (`venueKind: 'pool'`), `trade-settings-popover.tsx`, `amount.ts` (`parseAmountSafe`/`applySlippage`), `decodeTradeError.ts`.
- **Reused with a new call shape, no code changes needed:** `use-token-allowance.ts` — already takes an arbitrary `spender` and forwards whatever `amount` its caller passes to `approve()`. The V4 panel calls it with `spender = Permit2Address` and `allowance.approve(maxUint256)` instead of `allowance.approve(amountIn)`; the hook itself needs no modification.
- **New, V4-specific:**
  - A Permit2-signing hook: reads `Permit2.allowance(owner, token, UniversalRouter)` (returns `(amount, expiration, nonce)`); if `amount >= amountIn` and `expiration` is still in the future, skips signing entirely; otherwise builds an `IAllowanceTransfer.PermitSingle` EIP-712 message (using the read `nonce`) and calls wagmi's `useSignTypedData`.
  - `v4-swap-panel.tsx`, parallel to `swap-panel.tsx`: on submit, gets a fresh signature from the hook above, ABI-encodes the `V4_SWAP` command/actions and the Permit2 signature into `execute()`'s `inputs`, and submits via the existing `useTradeSubmission()` pattern.
  - A `V4_SWAP` quote hook parallel to `use-swap-quote.ts`, calling `MixedRouteQuoterV2.quoteExactInputSingleV4` (not a simulation of the real swap call, unlike V3 — see "Quoting" above) before enabling the submit button (same disabled-until-quoted pattern as every other panel — this is also the safety net against a Pools-tab V4 pool whose hook is not controlled by Pons and happens to restrict trading: a hook that blocks it will simply make the quote call revert, exactly like any other quote failure already does, rather than needing a dedicated hook-permission check).

Swap output always settles to the connected wallet's own address (the `TAKE_ALL` action's recipient — the same `recipient`/`msg.sender` convention every other panel in this app already uses). There is no separate claim/sweep step for the user.

## Still open, to verify during implementation (not blocking spec approval)

- **Native ETH handling.** V4 pools can hold native ETH directly as a currency (unlike V3, which always requires WETH). Whether `execute()` needs an explicit `WRAP_ETH` command or simply accepts native `value` directly into `V4_SWAP`'s settlement is Universal Router's documented, standard behavior — not independently confirmed with a real native-ETH sample on this specific deployment (same evidence gap the V3 spec flagged for its own native-ETH assumption). The implementation plan's first task must do one bounded `eth_call` simulation with real `value` before relying on it.
- **Exact `V4_SWAP` actions encoding on this deployment.** The action byte constants used (`SWAP_EXACT_IN_SINGLE = 0x06`, `SETTLE_ALL = 0x0c`, `TAKE_ALL = 0x0f`) are Uniswap's long-stable, documented `v4-periphery` `Actions.sol` values — not yet decoded against a real non-trivial swap transaction on this exact Universal Router instance, since no top-level transaction in the research sample called it directly (all went through AA/wrapper layers that this public RPC's lack of `debug_traceCall`/`debug_traceTransaction` access could not unwrap). The implementation plan's first task must do one bounded `eth_call` simulation against a real pool before relying on this encoding for a real submitted transaction.
- ~~Permit2 nonce read method~~ — resolved during planning: `AllowanceTransfer`'s `nonce` comes from `Permit2.allowance(owner, token, spender)`'s third return value, a live view read, not a client-generated value.
