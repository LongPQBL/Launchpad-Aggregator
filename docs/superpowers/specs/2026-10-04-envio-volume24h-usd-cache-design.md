# Envio-backed cache for official 24-hour USD launch volume

Date: 2026-10-04
Status: design for owner review

## Intent and decision

The owner wants the `All` launch list to rank by official 24-hour USD volume without repeating a large historical-price join on every request. New launches, transaction pages, and price reads must retain priority over summary maintenance. The chosen approach is to **recompute only launches affected by a change**, coalesce repeated changes, and store one current ranking result per launch. This is Envio-fed work in the `be/` database; the removed RPC-scan indexer is not part of the design. This spec changes the read model for `sort=volume24hUsd`, not the definition of official volume or the future `Pools` section.

The owner prefers the ranking to update as quickly as resources allow, without competing with more immediate features. The target is that a trade already committed to the `be/` database and with its historical price available reaches the ranking within 60 seconds under the benchmark workload. This is a measured normal-operation target, not a promise that an onchain trade appears within 60 seconds: `syncEnvioStagingLoop.ts` currently polls Envio every 15 minutes by default. Changing that ingestion interval is a separate decision and must be measured for its effect on new launches and transactions. For context, [GeckoTerminal's documented top-pool API refreshes every 30 seconds](https://docs.coingecko.com/reference/top-pools-contract-address); [Uniswap Explore documents volume ranking](https://support.uniswap.org/hc/en-us/articles/9818094509453-How-to-use-the-Uniswap-Explore-page) without publishing a per-trade refresh guarantee. These references inform the target but do not describe this app's data latency.

The owner also chose natural pagination: each page reads the latest published ranking. A token may move between requests and appear twice or be skipped across a page boundary. The UI does not force a restart at page one. A new visit or reload sees the latest rank. This matches the existing ranking's explicit allowance for late trades, prices, and reorgs; a fixed cross-page snapshot would require additional storage and is outside this change.

## Evidence and alternatives

The current `be/src/api/store.ts` reads all matching launches and all official trades in the 24-hour window, joins each trade to its verified quote/USD feed and historical round, then ranks in Node. In the disposable benchmark database with 5,001 launches and 5,500,001 trades, about 180,200 trades fell in the window. Warm list requests took 4.1–6.1 seconds; the first cold request took 138.6 seconds. The frontend request timeout is eight seconds, and the benchmark's safety target is three seconds. `EXPLAIN ANALYZE` showed indexed access but repeated launch/feed lookup per matched trade; the trade-price query alone took about 2.2 seconds and 1.47 million buffer hits. The test has fewer launches than the roughly 160K+ launch scale already discussed for the real database, so both dimensions need coverage in the next benchmark. The exact evidence is in `2026-10-04-volume24hUsd-perf-followup-brief.md` and the benchmark ledger linked there.

Three approaches were considered:

1. Rebuild every launch's score on a timer. This is easy to reason about but repeatedly scans unaffected launches and can compete with Envio and the API. It also leaves the cold refresh cost in a background job.
2. **Chosen:** enqueue each affected launch and recompute its score from authoritative trades, venue history, coverage, and price rounds. Repeated events for a launch collapse into one recomputation. The request reads a compact indexed result. A very active launch can still cause expensive rescans, so worker throughput is an acceptance gate.
3. Persist every trade's valued USD contribution and add/subtract contributions as trades arrive or age out. This minimizes repeated reads at high throughput but requires exact inverse operations for reorgs, late oracle rounds, feed changes, and expiry. Introduce it only if measured recomputation cannot meet the gates below.

## Stored read model and ownership

Add an additive `launch_volume24h_usd` table keyed by `(chain_id, token_address)`, with a foreign key to the launch, `volume_usd` as a decimal/string-compatible value, rank category (`positive`, `zero`, `null`), `computed_at`, `window_end`, `next_expiry_at`, completeness reason, and a monotonic revision. Copy the launch's block/transaction/log position into this read model so the rank index includes all tie breakers, including the large zero and null tails. Keep that position in sync when Envio replaces a launch in a reorg. `volume_usd` is nullable; a complete, trade-free window stores exact zero. Keep the existing approximate flag for positive historically priced values. Index the rank category, descending numeric score, and launch-position tie breakers so unfiltered pages can use keyset pagination and `LIMIT` in SQL. Filters remain server-side and apply before ranking. Search and filtered paths must be benchmarked; add only indexes justified by their measured plans.

Add a durable, deduplicated work table keyed by launch with `revision`, `due_at`, retry state, and error/lease metadata. A change to one launch increments its revision and moves its due time earlier; repeated changes do not create unbounded jobs. Worker claims bounded batches using row locks, recomputes from the authoritative tables, and publishes a result only if the revision it claimed is still current. A newer invalidation wins and remains queued. Crashes or lease expiry retry safely. The worker runs outside request handlers and outside Envio's transaction, with its own small connection/concurrency budget. It may wake immediately after a write, but it must also poll for missed notifications and due work; an in-memory event alone cannot be the correctness mechanism.

The cache is a derived read model. `trades`, `venues`, `launches`, `sources`, `quote_usd_feeds`, and `quote_usd_price_rounds` remain authoritative. No RPC call is made while ranking or recomputing a launch. The original read-side calculation remains available to integration tests and an offline reconciliation command during rollout, rather than being an unbounded production request fallback.

## Invalidation and recomputation

Enqueue the affected launch keys durably in the same `be/` database transaction that commits Envio-derived trade, venue, launch, or lifecycle changes. `reconcileReorgWindow` deletes and rebuilds the last 500 blocks; collect keys from both deleted rows and newly written rows. A launch with only deleted trades must still be invalidated. Coalesce the keys once per sync transaction instead of writing a job per trade. Staging-only Envio sync does not maintain the real-table cache.

When a verified feed mapping changes or price rounds are inserted or corrected, invalidate the launches with official trades in the affected 24-hour interval and quote asset/feed. Refactor the existing price upsert functions so the price write and invalidation commit in one database transaction; a crash after writing a price cannot leave an old score permanently. Feed discovery and round backfill continue through the existing `quotePricing` jobs. A missing round that later arrives can turn `null` into a number; a revoked or changed mapping can turn a number into `null` until repriced.

Coverage changes are also ranking changes. Track the launch's relevant factory, lifecycle, and official-venue source status against the Envio-aware safe head. When source progress/gaps change the completeness decision, mark affected cached rows `null`/updating and enqueue their keys in the same source-progress transaction. Use set-based SQL for this invalidation; process the resulting recomputation queue in bounded batches. The worker publishes a new known score only after recomputation. A transient worker failure leaves the row updating and never converts missing data to zero. Monitor large source-wide invalidations so they do not monopolize DB connections.

At each recomputation, use one `window_end` and the exact window `[window_end - 86400, window_end]`. Query only this launch's official venue trades; include executed protocol buybacks/internal swaps already stored as trades once, and exclude unrelated pools and non-trade transfers. Use each trade's recorded quote-asset address and the verified latest price round at or before its exact `(block_number, log_index)` as `valueTradeUsd`, with the same 24-hour round age rule. One unpriceable positive trade makes the whole USD total `null`; incomplete coverage also gives `null`; complete coverage and no trades gives `0`. The implementation must share or prove parity with the trade-page valuation rule so a trade's displayed historical USD value agrees with its contribution to volume. Keep numeric precision and output formatting consistent with the existing API contract.

Persist the earliest `trade.timestamp + 86401` still in the window as `next_expiry_at`: timestamps are integer seconds and the lower boundary is inclusive, so a trade first leaves the window one second after its 24-hour anniversary. Its due time enqueues the launch even if no new trade occurs, so the rolling total decreases naturally. Tests must cover the boundary without double-counting or an endless immediate retry. A periodic sweep also detects overdue expiries and lost work. Work scheduling can prioritize new trade/launch and price corrections over routine expiry while respecting the freshness target.

## API, pagination, and user-visible freshness

`GET /v1/launches?sort=volume24hUsd` reads the materialized score and orders globally in SQL: positive USD descending, then known zero, then null, with launch recency and `(chain_id, token_address)` as deterministic tie breakers. Keep `sort=recent`, launch detail, transactions, and the future `Pools` metrics independent. Only the selected page's other expensive statistics are computed. No per-request scan across the 24-hour trades and no Node sort of all launches remains on the production volume path.

Version the signed volume cursor for the new indexed order. It contains the last rank key and issue time, is bounded in size and lifetime, and rejects tampering/sort mismatch. Do not claim its old `asOf` freezes a ranking that now updates between requests. Use keyset comparison against the latest published cache. The documented tradeoff is possible duplication/omission if ranks change while the user pages; the UI leaves pagination alone and normal reload shows the latest list. Reject malformed or obsolete cursor versions with a clear client error, not an expensive fallback query.

Add `officialVolume24hUsdAsOf: string | null` to the list response and OpenAPI: it is the published `window_end` for a known score and `null` for an updating or unavailable one. The existing `officialVolume24hUsd` is `null` while a row is invalidated, and `officialVolume24hUsdApprox` is then `false`. If the cache has not completed its initial backfill or the worker heartbeat is more than two minutes old, the volume-sort endpoint returns a prompt 503 with `Retry-After`, rather than a frozen ranking; `sort=recent`, new-launch visibility, and transaction pages continue to work. The frontend handles this state without an eight-second wait and does not suggest per-block or per-trade real-time ranking. No new tab or Pools feature is added here.

## Rollout, operations, and verification

Use additive migrations. Backfill the cache in bounded batches, prioritizing active and new launches, while the current ranking path remains live. Verify parity before switching the API to the cached path; switch only after the cache is complete enough to rank the full filtered launch set, including zero and null tails. A failed initial backfill cannot silently omit launches. Do not migrate or delete historical prices, quote-feed jobs, or user data. No production deployment is part of implementing this spec unless separately requested.

Measure separate latencies: Envio source-to-`be/` ingestion, trade/price commit-to-invalidation, invalidation-to-cache publication, and cache publication-to-frontend refresh. This prevents a 60-second cache target from concealing the current 15-minute Envio sync interval. Log queue depth, oldest job age, retry count, worker duration, cache age, and reconciliation mismatches. Bound worker concurrency and DB connections, and pause or reduce batch size when DB contention affects new launches, transaction reads, or price jobs.

Integration tests on PostgreSQL must cover trade insertion, multiple trades coalescing, expiry with no new trade, official venue transitions, reorg deletion with no replacement, reorg replacement, late and corrected oracle rounds, feed remapping, incomplete coverage, `null` versus zero, retries/crash between source write and publication, idempotence, and cursor/filter ordering. Compare a sample of cached scores against the authoritative read-side computation and per-trade historical USD values. Do not mock `pool.query` for tests that rely on the real schema.

Re-run the synthetic benchmark at least at 5.5 million trades / 180,000 trades in 24 hours, and add a scenario near the real 160K+ launch count plus a concentrated high-volume launch. Measure first and later pages, search/status/chain filters, cold and warm reads, concurrent requests, and the worker while Envio/price jobs are active. The cached list's warm p95 must be under the existing three-second safety gate and cold requests must stay under the eight-second frontend timeout. The normal-operation trade-commit-to-published-rank p95 target is 60 seconds when price data is ready; report worst-case backlog as well. The worker must not make the measured p95 for Envio's new-launch/trade commit path or transaction/price reads exceed their established baseline by more than 10% under the same concurrent load. If this design fails those gates, retain the old API path only for comparison, profile the bottleneck, and plan the per-trade contribution approach as a separate design change.

## Scope boundary

The score here is a Pons launch's **official venue** USD volume. The future `Pools` section may reuse verified feeds, historical rounds, valuation rules, and scheduling patterns, but each pool's 24-hour volume is computed from that pool's own swaps under a separate metric. Do not merge all-pools volume into `officialVolume24hUsd` or count a swap twice. This spec does not change the quote-price discovery policy, Envio's raw pool ingestion, the 15-minute sync configuration, wallet/trading features, or live infrastructure.
