# Envio launch coverage, pool catalog, and database retention

**Date:** 2026-10-05
**Status:** Design for review. Implementation requires separate plans for coverage, Pools, and storage migrations.

**Implementation checkpoint:** Official Pons candles are now persisted from app trades by a bounded worker, with a resumable backfill and dirty-minute tracking. After backfill completes, the API reads stored candles and derives 52-week high/low from daily candles plus minute candles at the two window edges. Unpriced or pending minutes keep those results incomplete. These changes are in commits `b771ed0` and `9b09336`; migration `0027` and the historical backfill have not been run on the real app DB. No trade archiving or deletion has started. Launch parity, the general pool catalog and Pools UI, column/storage cleanup, and archive/retention implementation remain separate work.

## Goal and boundaries

When Envio finishes scanning the configured Robinhood Chain range, every launch emitted by a **configured Pons factory** must exist in Envio and eventually in the app database. The launch homepage lists Pons launches and measures each against its Pons-designated trading venue. A separate Pools section lists indexed pools; a Pons token detail page shows only pools whose currency pair actually contains that token. Database growth must be controlled without making older transactions, charts, or audit/reorg recovery silently disappear.

This is an eventual-completeness requirement, **not a claim that the development database already contains every launch**. Source coverage must be reported separately from current sync progress. Envio is the only new chain indexer. The [near-realtime sync design](./2026-10-05-envio-near-realtime-sync-design.md) and [24-hour volume cache design](./2026-10-04-envio-volume24h-usd-cache-design.md) remain separate work units. Historical quote/USD valuation uses the previously agreed trade-time price rule.

## Evidence and current limits

`envio/config.yaml` listens for `TokenLaunched` on V1 legacy `0x0c37…77a4` from block 8,600,612 and V1 active `0xA5aA…1feB` from block 8,991,118. It also listens for `TokenLaunchedV2` on V2 `0x7eD5…EC7e`; the chain start block 8,600,612 precedes the V2 deployment block 26,841,846 recorded in `be/src/launchpads/pons/sourceRegistry.ts`. The handlers persist each launch with chain, factory, token, block hash, transaction hash, and log index. Pons' [V1 contracts and event documentation](https://docs.ponsfamily.com/) lists the two V1 factories and says to index `TokenLaunched`; the [official Pons contracts repository](https://github.com/ponsdotdev/pons-labs/blob/main/README.md) lists the V2 factory; the [V2 integration documentation](https://docs.ponsfamily.com/v2) says indexing its factory yields every V2 launch. The “V3 factory” named in the V1 docs is the **Uniswap V3 pool factory**, not a third Pons launch factory.

Thus the present configuration is capable of capturing all launch events from these three known addresses once its range is processed. That statement has three limits: a new Pons factory must be added, an upstream gap or failed Envio handler must be repaired, and app sync must promote every raw launch successfully. The current app DB or a displayed head block alone proves none of these. The V1/V2 app-sync code currently rereads entire raw tables and performs blocking RPC enrichment before new launch insertion, so a transient RPC failure can delay promotion; the near-realtime design addresses that path.

The app database currently contains 166,400 launches, 3,469,064 trades, and 3,637,048 legacy `raw_logs` rows. Its `venues` table contains Pons-designated venues only: 144,488 V3, 21,912 curves, and 79 V4 pools. `trades` uses about 3.55 GB and frozen legacy `raw_logs` about 5.55 GB, including indexes. These are local read-only measurements on 2026-10-05, **not an on-chain completeness count**. Envio's own DB was not running for a full-range parity check.

## Coverage and reconciliation

Maintain a versioned launch-source registry with chain ID, factory address, event signature, deployment/start block, protocol version, and enabled status. Keep `envio/config.yaml`, the backend source registry, and the list shown by the coverage audit consistent. Adding a factory is a deliberate configuration/reindex operation; alert when official Pons contract docs change and review the new address before claiming coverage. A Pons V2 source starting at chain block 8,600,612 is safe but needlessly scans an earlier range; moving its start to the verified deployment block is an optional Envio rebuild optimization, never a reason to exclude earlier evidence.

For each known factory and a fixed finalized block fence, compare three sets of canonical event keys `(chainId, factoryAddress, txHash, logIndex)`:

1. Independent bounded `eth_getLogs` or HyperSync query from that factory's start block through the fence, using its exact launch topic and a second provider/sample check where feasible.
2. Envio `RawLaunch` or `RawLaunchV2` rows through the same fence, with block hash retained for reorg checks.
3. App `launches` rows promoted from Envio, keyed by source event identity rather than token count alone.

Persist range-level counts, first/last block, missing/extra event keys, and the Envio/app processed watermarks. An event missing at layer 2 is an Envio ingestion or configuration issue; present in layer 2 but missing at layer 3 is an app-sync issue. On mismatch, replay only affected bounded ranges and keep the source marked incomplete until parity is restored. A launch with pending metadata still counts as promoted once its minimal chain-derived record exists. Repeat this audit after initial backfill, factory changes, reindex, and periodically on finalized ranges. Alert on unknown factory addresses found in the maintained Pons source list, a stalled cursor, or nonzero parity difference. Never equate “Envio reached head” with “all launches visible” without this reconciliation.

Use chain/log identity and block hash for duplicate prevention and reorg repair. The latest 500 blocks remain provisional; finalized-range parity excludes them or separately marks them provisional. Tests cover all three factories, start-block boundaries, duplicate logs, missing raw rows, raw-to-app promotion failures, reorg replacement, and a new factory not yet registered.

## Official venues and other pools

Keep two concepts in the data model:

- A **Pons-designated venue** is the V1 pool emitted by its `TokenLaunched`, the V2 curve emitted by its launch, or the V4 pool proven from `PoolGraduated` and the matching `PoolManager.Initialize` pool key. Existing `venues.official` represents this relation. The label in the UI should say “Pons venue” or “Pons-designated pool,” without implying this aggregator is operated by Pons.
- A **discovered pool** is a verified pool on a supported DEX/chain, with protocol version, pool address or V4 Pool ID, `currency0`, `currency1`, creation block, fee/hook fields where applicable, and its own coverage state. Discovery alone does not make it a Pons-designated venue.

The launch homepage queries launch records only. Its 24-hour volume and ranking include only that launch's Pons-designated venue trades across its lifecycle: V1 V3, or V2 curve followed by its verified V4 pool. A trade belongs once to its pool/curve event key. Other pools containing the launch token do not raise that homepage volume. The Pons token detail keeps the official chart, price, and transaction feed scoped to designated venue history, then adds a clearly separate **Pools** section, like the Pools section on a Uniswap token page, for all indexed pools containing that exact token. This section includes the Pons-designated pool when indexed and any other supported pool containing the token; label the designated pool so users can distinguish it. Each pool row links to that pool's detail page and shows its pair, DEX/version, 24-hour USD volume, TVL when computable, and freshness/coverage indicator. A pool is shown on a token page only when `(chainId, tokenAddress)` matches its `currency0` or `currency1`, never because its Pool ID resembles a known launch or it traded in the same transaction.

Selecting a pool from the Pons token detail or global Pools page opens a **pool detail page** keyed by chain, protocol, and verified pool address/Pool ID. A link from a token detail preserves that token as the displayed side of the pair; a link from the global Pools page defaults to `currency0`, with a control to switch sides. The page presents the familiar token-detail data in the context of that pool: both token identities and contract links; the displayed token's price in the other pool currency and in USD when a verified conversion exists; price change and chart; 24-hour volume, TVL/liquidity, and available high/low figures; and a paginated transaction feed. Price, chart, volume, high/low, and transactions on this page use only that pool's swaps, while shared token facts such as name, symbol, logo, and supply remain token-level facts and are labeled accordingly. For a Pons token, keep a link back to its main token detail. A pool with missing price history or coverage shows `—` and an incomplete/pending state for affected metrics, never another pool's values or a current USD price applied to an old trade.

The global Pools page lists all **supported, verified, indexed** pools, including Pons-designated pools. It does not promise every pool on Robinhood Chain until discovery sources for all relevant protocols are configured and audited. Envio already persists every `Initialize` and `Swap` from the configured Uniswap V4 PoolManager without a Pons Pool ID filter. The app currently promotes only verified Pons V4 pools; a separate pool-catalog sync must promote the remaining V4 initializes and swaps. For Uniswap V3/V2 pools outside Pons, add separate Envio factory/pool event sources, deployment blocks, and parity audits before claiming those versions are covered. Do not infer an unindexed V3/V2 pool from token metadata or a search result. Pools outside a Pons launch can appear globally; only pools with an exact token-side match appear on that launch's detail page.

For V4, derive/verify Pool ID from the ordered currencies, fee, tick spacing, and hook, then key pool rows by `(chainId, protocol, poolId)`; preserve native ETH as the zero address and map it to a display asset only at the UI boundary. For V3/V2, verify pool address and token ordering against the appropriate factory/pool event. Store a chain-scoped normalized `(poolId, tokenAddress)` membership index for both sides; a Pons launch token must match by exact address. If a pool has no reliable USD oracle for its currency pair, show native amounts and `—` for USD metrics, not zero. Quote/USD resolution and historical trade valuation follow the existing historical-pricing spec; do not reuse today's USD price for old transactions.

This follows a visible pattern: [Uniswap Explore](https://support.uniswap.org/hc/en-us/articles/9818094509453-How-to-use-the-Uniswap-Explore-page) separates tokens, pools, and transactions, while [Uniswap token details](https://support.uniswap.org/hc/en-us/articles/9818052307341-What-is-the-Token-Details-page) has a pools section on the token page. [CoinGecko's top pools by token endpoint](https://docs.coingecko.com/reference/top-pools-contract-address) likewise keys discovery to the token contract address. Those products' token-level aggregate metrics need not determine this app's Pons-designated homepage metric.

## Research: recent trades versus old history

Public trading products expose different windows for hot feeds and historical access. [CoinGecko's on-chain trade endpoint](https://docs.coingecko.com/changelog/10122018) returns at most the latest 300 pool trades within 24 hours. [Binance Public Data](https://github.com/binance/binance-public-data) publishes daily and monthly downloadable trade and kline files. [Coinbase](https://help.coinbase.com/en/coinbase/getting-started/getting-started-with-coinbase/2fa-transaction-history-eu) still exposes transaction history older than 90 days, with extra verification for some users. The [Uniswap V4 subgraph](https://github.com/Uniswap/v4-subgraph/blob/main/schema.graphql) models individual swaps alongside daily pool aggregates. These are documented product/API or data-model behaviors; none proves the vendor's private DB deletion schedule. The useful pattern is a fast recent feed, compact historical aggregates, and a separate path to older detailed records.

Three possible retention strategies for this app:

| Strategy | PostgreSQL growth | Old transaction browsing | Main cost/risk |
| --- | --- | --- | --- |
| Hard-delete old swaps after keeping candles | Bounded | Stops at cutoff | Loses exact old trade list and audit evidence |
| Delete from PostgreSQL after verified object-storage archive | Bounded | Available through slower archive pages | Archive storage and reader complexity |
| Delete and refetch old swaps from chain/HyperSync on demand | Bounded | Possible only while provider serves the range | Rate limits, latency, provider dependence, repeated decoding |

Choose the second strategy. Chain re-fetch is a repair fallback, not the normal older-page path. Envio states [HyperSync serves full Robinhood Chain history](https://docs.envio.dev/blog/index-robinhood-chain-data), but availability and rate limits are external dependencies; the previous live probe already saw HTTP 429. Keeping the only old copy behind an on-demand provider would make history fragile. A hard cutoff would also contradict the user's requirement to browse older transactions.

## Storage: keep facts, remove duplication, and delete old DB rows after archive

Classify fields by their consumers before changing the schema. Keep immutable event identity, chain/block hash, timestamp, token/pool pair, exact raw amounts, trader/protocol-activity attribution, and enough price state to reconstruct API transactions, candles, 52-week high/low, volume, and reorg repair. Keep launch metadata and the field's read state so transient RPC failures can be retried. Keep historical quote/USD rounds needed for exact trade-time valuation or provide an auditable way to refetch older rounds when a user pages back. Do not store an unverified USD value as a permanent fact.

The Envio `RawSwap`/`RawV4Swap` schema still requires some `sender`, `recipient`, `liquidity`, and `tick` columns although current handlers write placeholder constants for fields their app hydrators do not consume. Measure column usage and bytes before removing any raw field. An Envio schema removal changes its entity fingerprint and can require a full Envio reindex, so schedule it only with a tested rebuild, retained backup, and parity audit. New pool math may need some fields that Pons-only hydration did not; verify consumer requirements before dropping them. In the app DB, `source_log_id` still references legacy `raw_logs` with cascade semantics. Drop or compact that relationship only after Envio parity, provenance migration, reorg-path testing, and backup; never cascade-delete active launches/trades by dropping old raw logs. The removed RPC indexer's `scan_jobs` table is a cleanup candidate after confirming no reader/writer and taking a backup. `candles` is now an active derived table and must be retained for historical charts and 52-week high/low; `phase_observations` may be removed only after reference checks.

The retention policy is **consumer based**, not a blanket “delete transactions older than 24 hours” rule:

| Data | Proposed policy | Gate before removal from hot app DB |
| --- | --- | --- |
| Launches, venues, pool catalog, lifecycle, source coverage | Retain for the life of supported sources | Never expire by age alone |
| Canonical trades/swaps and exact event keys | Keep recent rows in app PostgreSQL; archive older finalized rows outside PostgreSQL, then delete the DB copy | Verified archive, manifest/checksum, old-page API test, restore drill |
| 24-hour volume cache, short-lived UI notifications, completed retry jobs | Expire/recompute after their active window | Worker cursor advanced, no pending retry, audit metrics retained |
| Historical quote/USD rounds | Keep rounds required by current calculations; refetch older rounds on demand with provenance | No displayed historical USD value may silently change to current-price approximation |
| Legacy `raw_logs`, orphaned `scan_jobs`, unused derived tables | Remove after Envio equivalence and dependency audit | Backup, foreign-key migration, staged dry run, restore test |

Set an initial **90-day hot window** for the app's individual trades and pool swaps. It is an operational choice to test against real usage, not a claim about competitor retention. Keep 24-hour metrics and recent transaction pages entirely in hot tables. Keep compact hourly/daily pool and token aggregates for older charts, yearly high/low, and historical volume; derive them from finalized individual trades before those trades leave hot storage. A historical chart zoom or transaction page requiring exact old trades reads the archive. Retain trade-time quote/USD value and price-source provenance or the exact inputs needed to reproduce them in each archive record; do not revalue old trades with today's quote price.

Archive files are immutable, compressed, and outside both the app and Envio PostgreSQL databases, grouped by chain, source/protocol, time range, and pool/token lookup. A small PostgreSQL manifest stores each file URI, key/range bounds, row count, checksum, schema version, and verification state. The archive reader serves cursor pagination in `(blockNumber, logIndex, txHash)` order and merges a boundary page with hot rows without duplication. Archive requests may be slower, but must clearly show loading/failure and must never return an empty list as if there were no trades when the archive is unavailable. A recoverable object store is an implementation dependency; choose the provider and measure costs at implementation time, without binding the schema to a vendor.

For each closed time partition: wait until every source through that partition is complete and finalized; compute and verify aggregates; write archive files; compare exact event-key counts and checksums with the DB; exercise a sampled old-page query and restore; commit the manifest; **then delete the app DB's individual rows in bounded partition operations**. Keep a safety overlap above the 500-block reorg window and never delete an unresolved or pending-source range. Stop deletion and alert on any mismatch. A lifecycle policy may remove redundant daily files only after the monthly replacement passes the same parity checks; it must not delete the sole recoverable historical copy. PostgreSQL's [partitioning guidance](https://www.postgresql.org/docs/current/ddl-partitioning.html) supports detaching old partitions and moving them to cheaper storage more efficiently than row-by-row `DELETE`. Partitioning itself needs a benchmark and a migration plan: the current `(chain_id, tx_hash, log_index)` primary key cannot simply be reused unchanged on a time-partitioned parent, and cross-partition dedupe must remain exact.

The app-sync cursor must also record the archived finalized boundary per source. A restart or full replay must recognize already archived event keys and must not reinsert them into hot `trades` or incorrectly mark them missing from coverage. Historical reconciliation compares chain/Envio keys against the **union of hot rows and verified archive manifests**, with targeted file checks when a range disagrees. If an old source correction or deeper reorg is detected, invalidate the affected aggregate and archive manifest, rebuild from the canonical source, and publish corrected history before advancing its coverage again.

**Envio's raw DB is a separate growth source.** Deleting only app `trades` does not shrink `RawSwap`/`RawV4Swap`. Do not manually delete Envio-managed rows from a live HyperIndex schema: its replay, cursor, and reorg behavior must first be verified. The Envio storage work unit should benchmark two supported designs: (a) keep minimal per-event raw entities and archive/prune them through a proven Envio-compatible lifecycle, or (b) rebuild a lean Envio projection that keeps only live-window swaps plus durable aggregates while the app archive is the long-term event store. Either design must pass historical backfill, restart, reorg, launch parity, and old-page restore tests before switching. [Envio's own indexing example](https://docs.envio.dev/blog/index-hyperevm-data) demonstrates storing per-entity/day aggregates rather than one row per event when detailed rows are unnecessary. It does not establish that manual deletion of HyperIndex entities is safe.

[The Graph's pruning setting](https://thegraph.com/docs/en/subgraphs/developing/creating/subgraph-manifest/) concerns historical versions of mutable entities; it is not evidence that old Swap facts are deleted. We therefore avoid inferring a secret retention period from competitor UI limits.

## Implementation order and acceptance

1. Build the read-only launch parity command/report and record baseline for every configured factory at a fixed finalized block. Fix any discovered gaps before claiming completeness.
2. Implement incremental raw-to-app sync from the near-realtime design so Pons launches can appear before RPC enrichment and parity can converge without full-table passes.
3. Add the V4 pool catalog, exact token membership, pool-specific swaps/metrics, Pools API/page, Pons detail Pools section, and pool detail pages. Extend to V3/V2 only with new Envio discovery sources and explicit coverage labels.
4. Audit per-column use and measured storage, then migrate legacy provenance and remove truly orphaned data in small reversible steps.
5. Benchmark monthly trade partitioning and the 90-day hot/archive split. Enable **app DB deletion** only after old transaction pagination, charts, 52-week stats, historical USD values, parity checks, and restore behavior pass against real sampled data. Measure Envio DB growth separately and choose an Envio-compatible storage projection before pruning its managed tables.

Acceptance means: finalized-range launch parity is zero missing/extra events for each known factory; adding an unknown factory makes coverage visibly incomplete rather than silently “complete”; homepage volume excludes other pools; a Pons token detail lists every *indexed* pool containing its exact chain/address, and no unrelated pool; selecting any listed pool opens the matching pool detail with pool-scoped price, chart, metrics, and transactions; a pool trade contributes once to that pool's metrics; individual app-DB trades older than the verified hot cutoff are actually removed while their archived old-page results remain accessible at exact executed amounts and historical USD rules; no deletion happens before checksum/parity and restore gates; storage cleanup cannot delete a live launch/trade through a legacy foreign key; and Envio/app/UI coverage labels expose any unsupported protocol or incomplete range.
