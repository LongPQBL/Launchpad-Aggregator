# EIP-5792 Batch-Call Swap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** For wallets that report EIP-5792 atomic call-batching support, bundle the one-time `ERC20→Permit2` approval and the swap's `UniversalRouter.execute()` call into a single `wallet_sendCalls` request in the V3 and V4 swap panels, so a first-time swap needs one on-chain confirmation instead of two.

**Architecture:** A new `useCanBatchCalls()` hook wraps wagmi's `useCapabilities` and trusts only `atomic.status === 'supported'`. `use-trade-submission.ts` gains a `submitBatch` alongside the existing `submit`, backed by wagmi's `useSendCalls`/`useWaitForCallsStatus`, mapped onto the same `{status, txHash, errorMessage}` shape so `TradeStatus` needs zero changes. `ApproveOrActionButton` gains a `canBatchApprove` prop that, when true, skips its plain "Approve" step and goes straight to the normal action button. `swap-panel.tsx`/`v4-swap-panel.tsx` branch at their existing `submission.submit(executeCall, ...)` call site: batch when approval is needed and the wallet can batch, otherwise unchanged.

**Tech Stack:** Next.js, React, TypeScript, wagmi 3.7.7 (already exports `useCapabilities`/`useSendCalls`/`useWaitForCallsStatus` — no new dependency), viem 2.56.9, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-10-08-eip5792-batch-swap-design.md`

## Global Constraints

- Only `atomic.status === 'supported'` enables batching — `'ready'` and `'unsupported'` both mean "use today's two-step flow" (spec's "Wallet capability detection").
- The Permit2 `PermitSingle` signature is never batched — it stays a plain `signTypedDataAsync` call, obtained exactly as today, before either `submit` or `submitBatch` is invoked.
- No label change on the action button — it always reads `actionLabel` ("Swap"), batched or not (spec's "Button and submit-flow changes").
- Curve Buy/Sell panels (`buy-panel.tsx`/`sell-panel.tsx`) are out of scope — do not add batching there.
- `TradeStatus`, `decodeTradeError`, and the Permit2 signing flow (`use-permit2-permit.ts`) are reused unchanged — no edits to any of the three.
- Work directly on `main`, one commit per task (CLAUDE.md: solo developer, no worktrees).

## Review Focus

- A wallet reporting `atomic.status === 'ready'` (not `'supported'`) must still see the plain two-step Approve-then-Swap flow, never a batch attempt — this is the one status value most likely to be mistaken for "good enough" (Task 1).
- Every existing test file that renders a component using `useTradeSubmission` (`buy-panel.test.tsx`, `sell-panel.test.tsx`, `curve-trade-panel.test.tsx`, `launch-detail.test.tsx`, `pools.test.tsx`, plus `swap-panel.test.tsx`/`v4-swap-panel.test.tsx`) must keep passing unmodified once `useTradeSubmission` unconditionally calls the three new wagmi hooks — an un-mocked hook call is a silent crash risk, not just a missing assertion (Task 2).
- Calling `submitBatch` then later calling `submit` again (e.g. a second swap of the same token, once its allowance already covers the amount) must report the *single*-call status, not a stale batch status left over from the first swap (Task 2).
- `needsErc20Approval && canBatch` must render the same actionable "Swap" button `!needsApproval` already does — not a third visual state, and not still the plain "Approve" button (Task 3).
- The approve call and the execute call must land in the batch in that exact order (`[approveCall, executeCall]`) — a wallet that executes a non-atomic batch sequentially would otherwise try to pull funds before Permit2 itself is approved (Tasks 4 and 5).

```ts
'use client';

import { useAccount, useCapabilities } from 'wagmi';
import { robinhoodChain } from '@/wallet/config';

// Only 'supported' is trusted — EIP-5792 also defines 'ready' (the wallet could support atomic
// batching if the user opts in, not guaranteed) and 'unsupported'. Treating 'ready' as enough
// risks a wallet_sendCalls batch that doesn't execute atomically, which could land the approval
// without the swap.
export function useCanBatchCalls(): boolean {
  const { address } = useAccount();
  const { data } = useCapabilities({
    account: address,
    chainId: robinhoodChain.id,
    query: { enabled: Boolean(address) },
  });
  return data?.atomic?.status === 'supported';
}
```

**Interfaces:**
- Consumes: nothing new from other tasks.
- Produces: `TradeCall` (exported interface: `{ address: Address; abi: readonly unknown[]; functionName: string; args: readonly unknown[]; value?: bigint }`), `TradeSubmission.submitBatch(calls: readonly TradeCall[], options?: { onSuccess?: () => void }): void`. `TradeSubmission.submit` keeps its existing call shape (`submit(call: TradeCall, options?: { onSuccess?: () => void })`) but is now typed via the same `TradeCall` interface instead of `ReturnType<typeof useWriteContract>['writeContract']` — every existing call site (`buy-panel.tsx`, `sell-panel.tsx`, `swap-panel.tsx`, `v4-swap-panel.tsx`) already passes a plain `{address, abi, functionName, args, value?}` object literal, so this is a type-only change with no call-site edits required in this task.

  **Accepted tradeoff:** `writeContract`'s real wagmi type is generic over the ABI, which lets TS check `functionName`/`args` against the actual ABI at each call site today. Wrapping `submit` to also set `mode` (needed so `submitBatch` and a later `submit` don't read each other's stale status — see Review Focus) loses that per-call-site ABI checking in exchange for the simpler `TradeCall` shape. This is deliberate, not an oversight: the 4 call sites are already covered by this project's runtime tests (which would fail on a wrong `functionName`/`args` regardless of compile-time ABI checking), and the alternative — preserving `writeContract`'s exact generic type on the wrapper — runs into TypeScript's general difficulty assigning a concrete function implementation to a generic function *type*. If a cleaner typing is found during implementation that keeps both the ABI checking and the mode-tracking, prefer it; otherwise this tradeoff stands.

```ts
'use client';

import { useState } from 'react';
import type { Address } from 'viem';
import { useSendCalls, useWaitForCallsStatus, useWaitForTransactionReceipt, useWriteContract } from 'wagmi';
import { decodeTradeError } from './decodeTradeError';

export type TradeSubmissionStatus = 'idle' | 'pending' | 'confirming' | 'confirmed' | 'failed';

export interface TradeCall {
  address: Address;
  abi: readonly unknown[];
  functionName: string;
  args: readonly unknown[];
  value?: bigint;
}

export interface TradeSubmission {
  submit: (call: TradeCall, options?: { onSuccess?: () => void }) => void;
  submitBatch: (calls: readonly TradeCall[], options?: { onSuccess?: () => void }) => void;
  status: TradeSubmissionStatus;
  txHash: Address | undefined;
  errorMessage: string | null;
}

export function useTradeSubmission(): TradeSubmission {
  // Tracks which of submit()/submitBatch() was most recently called, so status/txHash/errorMessage
  // read the right underlying hook's state — both useWriteContract and useSendCalls' mutation state
  // persist across renders once used, so "a batch was sent at some point" is not a reliable signal
  // that the *latest* submission was a batch (e.g. a second swap of an already-approved token goes
  // through submit(), not submitBatch(), even in a panel that used submitBatch() once before).
  const [mode, setMode] = useState<'single' | 'batch'>('single');

  const { writeContract, status: writeStatus, error: writeError, data: writeHash } = useWriteContract();
  const { status: receiptStatus, error: receiptError } = useWaitForTransactionReceipt({ hash: writeHash, query: { enabled: Boolean(writeHash) } });

  const { sendCalls, status: sendStatus, error: sendError, data: sendData } = useSendCalls();
  const { data: callsStatus, error: callsStatusError } = useWaitForCallsStatus({ id: sendData?.id, query: { enabled: Boolean(sendData?.id) } });

  function submit(call: TradeCall, options?: { onSuccess?: () => void }) {
    setMode('single');
    // writeContract's real type is generic over the ABI for literal-argument inference; TradeCall's
    // simpler shape loses that inference, so this call needs a loose cast at this single internal
    // boundary. Every real call site still passes a concrete object literal, which is what actually
    // matters for correctness.
    writeContract(call as never, options);
  }

  function submitBatch(calls: readonly TradeCall[], options?: { onSuccess?: () => void }) {
    setMode('batch');
    sendCalls({ calls } as never, options);
  }

  let status: TradeSubmissionStatus = 'idle';
  let txHash: Address | undefined;
  let errorMessage: string | null = null;

  if (mode === 'batch') {
    if (sendStatus === 'pending') status = 'pending';
    else if (sendStatus === 'error') status = 'failed';
    else if (sendStatus === 'success') {
      if (!callsStatus) status = 'confirming';
      else if (callsStatus.status === 'success') status = 'confirmed';
      else if (callsStatus.status === 'failure') status = 'failed';
      else status = 'confirming';
    }
    txHash = callsStatus?.receipts?.[callsStatus.receipts.length - 1]?.transactionHash;
    const reportedError = callsStatusError ?? sendError;
    errorMessage = reportedError ? decodeTradeError(reportedError) : null;
  } else {
    if (writeStatus === 'pending') status = 'pending';
    else if (writeStatus === 'error') status = 'failed';
    else if (writeStatus === 'success') status = receiptStatus === 'success' ? 'confirmed' : receiptStatus === 'error' ? 'failed' : 'confirming';
    txHash = writeHash;
    const reportedError = receiptError ?? writeError;
    errorMessage = reportedError ? decodeTradeError(reportedError) : null;
  }

  return { submit, submitBatch, status, txHash, errorMessage };
}
```
